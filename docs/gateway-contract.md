# Native gateway contract

The combined helper is a small POSIX client, not a gateway implementation. Validate these interfaces in the **running** release before using it. Old gateways without them are unsupported; the helper does not fall back to `gateway_state.json` or process-name guessing.

## Observation

Hermes's gateway-owned control socket v1 accepts one JSON line per connection:

```json
{"verb":"identify","id":1,"protocol":1}
```

The `status` verb uses the same envelope. Replies are `{"ok":true,"result":{...}}`. The client uses `<gateway-home>/gateway.sock`, or the native `gateway.sock.path` indirection for long paths. The local OS user/filesystem is the trust boundary; do not point it at untrusted homes or socket pointers.

Required identity fields: protocol 1, positive PID, positive numeric process `start_time`, exact canonical `hermes_home`, and full lowercase 40-character `code_sha` on every observation, including before drain setup. Multiplex `served_profiles` advertisements are refused, because the helper does not establish per-profile work coverage within a shared gateway.

Required status fields: protocol 1, `answering_pid` matching identity, `gateway_state` of `running` or `draining`, and nonnegative integer `active_agents`. Boolean, missing, negative, or string counts are unknown, not zero. Socket failure aborts inspection/drain setup; replacement verification retries within its bounded observation window.

The socket proves a live responder; its status handler reads the gateway's maintained runtime-status record. The external-drain watcher refreshes aggregate work while draining. This is not an atomic cross-service snapshot, and a broken internal counter cannot be detected merely by validating JSON types.

In the inspected gateway, `_active_work_count()` includes messaging agents, gateway-owned cron jobs, and API-server runs. Those constituent helpers contain best-effort fallbacks, so **deployment acceptance must exercise each work source actually in use**. Independent CLI sessions, detached tool/delegate/kanban work, other backends, standalone cron processes, and unlisted profiles need separate inventory. `--other-work-stopped` records the operator's attestation; it is not proof generated by this helper.

## Reversible drain

Native `gateway/drain_control.py` defines `<gateway-home>/.drain_request.json`. The helper creates it exclusively with the native payload fields: `action: drain`, UTC `requested_at`, principal, `epoch`, and `suppress_notification: false`. It adds a non-secret `maintenance_ticket` UUID used only for cleanup ownership.

The reference macOS contract uses an empty epoch (native non-Linux fallback). Presence is recognized as a request; the gateway asynchronously enters external drain without terminating in-flight turns. **Do not interpret marker creation as acknowledgement.** `wait` requires `gateway_state: draining` and zero work from the live socket.

Native markers expire after an hour. The helper neither renews them nor promises a persistent lock across machine restarts; it refuses waits on markers older than 30 minutes. Complete the transition to stopped services promptly. Keep upstream admission closed until operator verification finishes.

`cancel` removes only existing regular files owned by the current OS user with this ticket, after checking all selected markers. It works while services are stopped. Absence is idempotent; a foreign, symlink, or corrupt marker is an error. A partial begin may leave markers for explicit cancellation. Crash during marker writing can leave a malformed file requiring manual investigation. No watchdog silently releases maintenance.

There must be **one operator**, no active legacy WebUI coordinator, and no other marker writer. The ownership checks prevent ordinary accidental overwrite/removal; they are not an OS transaction against hostile or concurrently changing same-user files. The original WebUI marker/registration race remains as described in [integration.md](integration.md#limits). Close ingress and stop both runtimes before code or dependency writes.

## Verification boundaries

`inspect` prints only selected runtime identities/counts, not session/response payloads. Store the output privately: paths, process IDs and code identities are operational metadata.

`wait` observes unchanged generations, owned markers, gateway drain acknowledgement, and zero work over the requested quiet period. This is **drained_observed**, not permission to ignore untracked work or reopen ingress.

`verify` requires replacement starts for every selected gateway and WebUI, gateways in running state at the exact expected full Agent SHA, and stable generations with healthy WebUI responses. It does not prove platform connectivity, WebUI loaded SHA, application/database compatibility, or an actual model turn. Its output is **replacement_observed**, not updated-and-healthy.

Timeouts bound polling; a final in-progress snapshot can add its finite per-probe I/O budgets (two seconds per socket request and HTTP call per selected runtime). This is an operator tool, not a hard real-time deadline. Wait errors retain drains; verify errors do not mutate anything. Runtime/transport errors return JSON with a coarse error type rather than dumping service bodies. Use the checklist and local native logs to diagnose, without copying secrets into a shared transcript.

## Provenance and acceptance

The native interfaces were inspected in Hermes Agent checkout `094280b582be94cdd51c92b1fd429cabb33770de`; this identifies the local source examined, not a recommended install revision or a claim every upstream release has the same behavior. Verify the interfaces, not just a version number. Relevant source owners are `gateway/control_socket.py`, `gateway/drain_control.py`, `gateway/run.py`, and `hermes_cli/build_info.py`.

Authoritative update behavior: [Hermes updating documentation](https://hermes-agent.nousresearch.com/docs/getting-started/updating). Upstream source: [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent). WebUI is a separate project; consult its version-matched supervisor/install guidance.

Before deployment, run the kit tests, then a disposable integration with the actual installed gateway and WebUI. Demonstrate busy messaging/API/cron work stays protected, new admissions are refused, drain cancellation resumes work, stopped services stay stopped during mutation, and both replacement/recovery generations pass real conversation checks. The kit's fixture suite alone cannot certify a recipient installation.
